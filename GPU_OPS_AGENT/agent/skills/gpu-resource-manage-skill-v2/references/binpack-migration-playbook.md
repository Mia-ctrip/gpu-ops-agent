# Binpack 迁移规划指南

当 Pod 需要多卡资源（如 8 卡训练任务）但集群中不存在可用的完整机器时，需要通过**驱逐部分 Pod 腾挪出满足需求的机器**。本文档是这类迁移决策的参考。

## 原理

机器A上有 3 个 1 卡 pod，占3张；机器B上有 1 个 4 卡 pod，占4张；机器C上有 1 个 8 卡 pod，占8张满；机器D上有 2 个 1 卡 pod，占2张。若需要一台 8 卡完整机器：

- 方案1（表面最优）：驱逐B上的4卡 pod → B腾出4张，合并其它4张 → 得到1台8卡机 ✓
- 方案2（备选）：驱逐D上的2个1卡 pod → D腾出6张，合并A已有2张 → 得到1台8卡机 ✓

看起来方案1只需驱逐1个 pod，方案2需驱逐2个 pod。但实际决策需要考虑：

- B 上的 4 卡 pod 可能是**线上单实例服务**，驱逐会中断全部流量；
- D 上的 2 个 1 卡 pod 可能是**多实例集群**，且有 DR 副本，中断短时间内无感知。

从这个接口无法判断业务性质，所以**必须给出多个备选方案**让用户自行判断。

## 迁移方案输出要求

当调用 `topology_query.py fragmentation` 或手工分析时，必须输出：

1. **最优方案**（驱逐 pod 最少的方案）的详细拓扑现状；
2. **2～3 个备选方案**及其拓扑现状；
3. 每个方案里**需要被驱逐的 pod 清单**（pod名+占用卡数）；
4. **迁移风险提示**："仅基于数据提供，实际风险需由运维人员根据pod业务性质判断"。

## 案例

### 场景
- 集群：阿里云上海(SHARE-SHA-ALI-PRO1)
- Namespace：Train
- 卡型：H20
- 需求：1 台 8 卡完整机器用于整机训练

### 当前拓扑

| 机器 | Allocatable | Available | GPUPodCount | 运行的 Pod |
|---|---|---|---|---|
| vmsali-01 | 8 | 5 | 3 | job-a(1卡) + adhoc-b(1卡) + ocppro-c(1卡) |
| vmsali-02 | 8 | 4 | 1 | adhoc-d(4卡) |
| vmsali-03 | 8 | 0 | 1 | ocppro-e(8卡) |
| vmsali-04 | 8 | 6 | 2 | job-f(1卡) + adhoc-g(1卡) |

**问题**：无单台可用 8 卡机，需要驱逐腾挪。

### 方案输出

```
【最优方案】驱逐 vmsali-02 上的 adhoc-d(4卡)
- adhoc-d 迁移到 vmsali-04 (剩余6卡足够)
- 结果：vmsali-02 腾出 8 卡完整机器

【备选方案 A】驱逐 vmsali-04 上的 job-f(1卡) + adhoc-g(1卡) 
- job-f/adhoc-g 可迁移到 vmsali-01 (剩余5卡足够2卡)
- 结果：vmsali-04 腾出 8 卡完整机器

【备选方案 B】驱逐 vmsali-01 上的全部 3 个 pod
- job-a(1卡) + adhoc-b(1卡) + ocppro-c(1卡) 可迁移到 vmsali-04 (剩余6卡不足3卡)
- 不可行（target 容量不足）

[迁移风险]
- 最优方案：需驱逐 1 个 4 卡 pod，若该 pod 是线上单实例服务会中断全部流量
- 备选方案A：需驱逐 2 个 1 卡 pod，若这2个都是多实例集群会影响较小
- 请根据实际业务性质（可查询 peta 平台）最终确定
```

## 脚本辅助

```bash
# 一键查看某集群某卡型的碎片化情况（按驱逐难度从小到大排序）
python scripts/topology_query.py <json文件> fragmentation \
  --cluster 上海阿里云 \
  --namespace 训练 \
  --cardtype h20
```

输出中 `GPUPodCount` 最少的机器优先级最高（需驱逐 pod 最少），但最终决策权在运维人员。
